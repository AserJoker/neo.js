# ADR-007: 开发规范与约束

- 状态: 已接受 (2026-11-02)
- 决策者: aserjoker（项目负责人） + CodeAgent
- 关联: ADR-006（异常即值）

## 背景

本项目进入设计/编码阶段，需要固化**语言开发层面的风格、约束与推论**。

## 决策

### 1. C++ 异常策略（精确版）

- **不通过编译选项禁用异常**（`-fno-exceptions` 会破坏标准库——
  `std::vector`/`std::string`/`std::bad_alloc` 等依赖异常机制）。
- **本项目自有代码禁止抛出/捕获异常**：不写 `throw`，不写 `try/catch`。
- **标准库必须有 try-catch 兜底**：标准库可能抛异常（分配失败、`at()` 越界等），
  在标准库边界用 try-catch 兜底，防止标准库异常泄漏到嵌入宿主。
- 本项目错误处理走**返回值/错误值通道**（与 ADR-006「异常即值」一致）。

### 2. 测试框架：git submodule 引入 GTest

- 使用 git submodule 引入 GoogleTest（依赖显式管理，不靠包管理器）。

### 3. 编译告警：警告即错误

- 启用 `-Wall -Wextra` 等，`-Werror` 将警告视为错误，强制高质量。

### 4. 指针与哨兵约定

- **禁止用 NULL/nullptr 作为哨兵占位**（尤其 Engine 内部）。
  应使用**业务语义的哨兵**——例如 Engine 中「无值」用 JS 的 `undefined`，
  而不是 C 指针的空。避免业务逻辑与 C 指针细节耦合。
- **非 C 对外 API（内部 C++ API）：默认参数可信**，不做防御性判空。
  内部调用是信任契约，保持性能。
- **C API（嵌入层对外边界）：参数不可信**，必须做判空校验。
  空指针直接 **panic**（编程错误，不可恢复，立即终止），不返回错误。

### 5. 内存管理模型

- 使用封装过的**统一分配器（Allocator）**实现统一的内存分配与销毁。
- 与 GC 分层：GC 是业务层（跟踪 Value 是否可销毁），
  实际内存分配/释放通过统一 Allocator 类完成。
- 详见 ADR-008（内存管理架构）。

### 6. 编码风格：组合优于继承，依赖注入

- **避免深度继承**，尽量使用**组合**，不利于未来演进。
- **依赖注入**：构造函数注入接口对象指针，对象持有后消费。

```cpp
class VM {
    Engine* engine_;  // 构造函数注入，持有后消费
public:
    explicit VM(Engine* engine) : engine_(engine) {}
};
```

- 收益：可测试性（可注入 mock）、可演进性（替换实现不影响消费者）、
  解耦（模块间依赖接口而非具体类）、可嵌入（宿主注入自定义实现）。
- **因此必须有代码设计阶段**：先设计组合关系与依赖注入方向，不能直接上手开发。

### 7. 源码编码与格式化

- **源码统一使用 LF 换行、无 BOM 的 UTF-8**。
- 通过 **`.gitattributes`** 声明（`* text=auto eol=lf`），保证跨平台一致。
- **开发时主动处理**：不只依赖 gitattributes，写入/编辑时就要保证 LF + UTF-8 无 BOM。
- 引入 **clang-format** 统一代码格式，`.clang-format` 配置文件，可 CI 校验。

### 8. 正确性纪律：双平台 + 内存工具

- 开发后**除保证用例正确**，还需在 **Windows 与 WSL 下都编译运行通过**（跨平台验证）。
- 使用 **Valgrind**（WSL/Linux 下）与 **ASan（AddressSanitizer）**（Windows/Linux 均可用）
  保证内存正确性（无泄漏、无越界、无悬垂）。
- 工具链分工：Windows 用 clang + ASan；WSL/Linux 用 clang/gcc + Valgrind + ASan。

## 推论

- 标准库边界统一用 try-catch 兜底，避免异常泄漏。
- 项目自有代码的错误处理风格统一为「返回值/错误值」通道。
- 模块依赖通过接口注入，设计阶段确定依赖图，避免深度继承。
