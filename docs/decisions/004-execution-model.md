# ADR-004: 执行模型 — VM 生命周期与栈模式

- 状态: 已接受 (2026-11-02)
- 决策者: aserjoker（项目负责人） + CodeAgent
- 关联: ADR-001（Engine/VM 分离）

## 背景

ADR-001 确立了 Engine（语言核心/状态）与 VM（执行中枢/控制流）分离。
本 ADR 进一步定义**执行模型**：VM 的形态、生命周期、与 Engine 的状态关系，
以及它们如何支撑挂起/恢复。

## 决策

### 1. 状态分层：Engine 持久 / VM 临时

- **Engine 持有持久化语言状态**（长期存活，跨任务）：
  作用域、变量、对象模型、标准库、调用栈、try 栈、label 栈。
- **VM 持有临时状态**（单次任务的 CPU 状态）：
  操作数栈、PC（程序计数器）、临时寄存器。

### 2. VM 采用栈模式（stack-based）

- 操作数在**栈上计算**（不是寄存器模式）。
- 字节码指令从操作数栈弹出操作数、压入结果。

### 3. 栈平衡不变量（statement 保证栈平衡）

- **每条 statement 执行前后，操作数栈深度必须一致**。
- 这是字节码正确性的核心不变量，也是挂起/恢复成立的前提：
  挂起点只可能出现在 statement 边界，恢复时栈深度可预期。

### 4. VM 生命周期：一次任务一个 VM

- **每次函数调用 / 模块执行 → 创建一个 VM 实例**。
- **彻底执行结束（函数 return / 模块 halt）→ 销毁 VM 实例**。
- VM 不代表整个 CPU，而代表**一次任务的 CPU 状态**。

### 5. 挂起/恢复：Engine 与 VM 两者都保存

- 挂起（协程 yield / async await / 生成器暂停）时：
  **Engine 状态（作用域、调用/try/label 栈所在帧）+ VM 状态（操作数栈、PC）都要保存**。
- 恢复时：重建 VM 的栈与 PC，回到 Engine 对应的状态帧，继续执行。

## 推论

- 协程/生成器/async 任务各自是**独立的 VM 实例**，天然可挂起可恢复。
- VM 是轻量可创建可销毁的临时对象，不是全局单例。
- 挂起只发生在 statement 边界（栈平衡保证），使状态保存变得简单可预期。

## 后果

- 优点：任务隔离清晰、挂起恢复简单可靠、VM 可随时创建销毁、Engine 可长期复用。
- 缺点：函数调用/模块执行需要创建/销毁 VM（有少量开销）；需要严格遵守栈平衡不变量。
