# ADR-001: 运行时整体架构与核心技术选型

- 状态: 已接受 (2026-11-02)
- 决策者: aserjoker（项目负责人） + CodeAgent
- 关联: [ADR-002: GC 抽象](#), [ADR-003: Unicode 策略](#), [ADR-004: 执行模型](#), [ADR-005: native 等价性](#), [ADR-006: 异常即值](#), [ADR-009: 源码结构与 API 风格](#), [ADR-011: Engine 组织架构](#)

## 背景

从零自研一个可嵌入的 ECMAScript 标准运行时（只有 JS 标准库，无 Node 标准库），
本体作为嵌入库供其它项目使用，允许外部注册自定义模块。

动机：
- V8 等大厂引擎不适合嵌入：依赖复杂、构建体系庞大（GN/ICU/内置工具链），二次开发成本高。
- QuickJS 等社区项目工程能力弱：标准支持不完整、调试等外部功能不全、历史包袱长、治理弱。

## 决策

### 1. 引擎架构：字节码 VM（强制）

不使用 AST 解释器。理由（项目负责人提出，经验证正确）：

> 异步协程、生成器、`yield`、`await` 等特性需要执行中保存/恢复执行状态。
> AST 解释器用 C++ 递归栈，挂起恢复会变成地狱；字节码 VM 用显式栈帧，
> 天然支持挂起恢复（保存 PC/栈帧/寄存器即可）。

因此架构为（五阶段，含 Sema；Lexer 与 Parser 合一）：

```
JS 源码 → [Lexer + Parser 合一](AST) → Sema(标注+语义检查) → Compiler → 字节码 → VM 执行
```

### 1a. Lexer 与 Parser 合一（扫描器随解析器推进）

JS 词法**依赖语法上下文**，无法独立地、无上下文地把源码切成 token 流。
最典型：`/` 是除法还是正则字面量开始，取决于前一个 token 的语法角色
（`a / b` 是除法，`x = /abc/` 是正则）。

因此 **Lexer 不能作为独立前置阶段**，必须与 Parser 合一：

- Parser 持有扫描器状态，解析时按需拉取 token。
- 在需要正则字面量的位置，Parser 通知扫描器以「正则模式」切词；
  在需要运算符的位置，以「除法模式」切词。
- 这也是 V8 等的做法（parser 驱动 scanner）。
- 扫描器内部仍独立实现 token 识别逻辑，只是**推进时机**由 Parser 控制。

### 1b. Sema 阶段（语义分析 + AST 标注）

Parser 只保证**语法正确性**。Compiler 需要比语法更多的信息，
因此 Parser 与 Compiler 之间必须有 **Sema** 阶段，两个职责：

1. **语义检查**（Parser 无法覆盖的静态错误）：
   - 未定义变量引用（严格模式 / 全局降级规则）
   - 严格模式违规（`with`、重复参数、八进制、`delete` 标识符等）
   - TDZ（暂时性死区）：`let x = x`、`const` 重复赋值
   - 同作用域重复声明、`break`/`continue`/标签匹配、`return` 位置合法性
   - 控制流/数据流分析（不可达代码、返回值路径完备性）

2. **AST 标注**（把 JS 隐式语义变成编译器可消费的显式信息）：
   - **闭包收集**：JS 闭包是隐式词法捕获，Compiler 需要**显式捕获列表**。
     每个标识符引用标注为 `Local / Captured / Global / Unresolved`；
     每个函数节点标注 `captured_vars`（显式捕获列表）。
   - 函数属性标注：`is_strict / is_generator / is_async / has_arguments / has_this`
   - 动态语义降级：直接 `eval` → 当前函数作用域变量保守标注；`with` → 动态作用域降级
   - 隐式全局：非严格模式未声明赋值 → 标注 `GlobalWrite`（运行时创建全局属性）

Sema 输出**标注后的 AST（annotated AST）**，Compiler 成为纯机械的代码生成器，
不需要再理解 JS 词法作用域语义。这与负责人此前 clux 项目的 `sema` 模块同构。

### 1c. Engine 与 VM 分离（语言核心与执行中枢解耦）

**语言核心（Engine）与执行中枢（VM）必须分离**，这是模块依赖方向的根本决策：

- **Engine（语言核心）= 状态持有**：负责「当前处于什么状态」——
  作用域（当前哪个作用域）、变量（有哪些变量）、调用栈、try 栈、label 栈在哪一帧，
  以及语言实体：Value / Scope / Context / Function / 对象模型 / 标准库。
  Engine 定义「语言是什么」。
- **VM（执行中枢）= 控制流**：负责「接下来执行哪条指令」——
  PC 跳转、分支、循环、异常跳转（字节码解释循环、指令分发）。
  VM 通过解析字节码，调用 Engine 的接口完成语言功能。
  VM 定义「语言如何执行」。

**依赖方向：VM → Engine**（VM 调用 Engine 接口；Engine 不依赖 VM）。

类比：VM 是 CPU（控制流），Engine 是内存/寄存器文件（状态）。
这解释了为何字节码 VM 天然支持协程挂起恢复——挂起时保存的正是 Engine 的状态
（栈帧/作用域/try栈/label栈），VM 的 PC 只是其中一值。

分层收益：
- Engine 可独立测试（不依赖 VM 即可验证 Value/对象/作用域语义）。
- VM 可替换（后续可换 JIT 或其它执行形态，Engine 不动）。
- 字节码只是 Engine 之上的执行形态，不是 Engine 的一部分。

### 2. 实现语言：C++（C++20）

- 工具链：clang++ 22.1.3 + CMake 4.3.1 + Ninja 1.13.2（已验证可用）
- 平台：Windows 11（当前），设计上跨平台

### 3. GC：抽象接口先行，一阶段 Mark-Sweep

- 第一阶段实现 Mark-Sweep。
- 必须设计 GC 抽象接口（`GCObject` 基类 + 根集枚举 + 对象图遍历回调），
  保证后期演进分代/增量 GC 时**不产生散弹式修改**（不把 GC 细节泄漏到每个对象实现里）。
- 详见 [ADR-002](002-gc.md)（待写）。

### 4. 自研边界

- 核心完全自研：Lexer / Parser / Compiler / VM / 标准库 / GC。
- **第三方依赖最小化**：核心引擎仅依赖 C++ 标准库。
- **Unicode 策略**：允许使用 ICU（业务无关基础库），且已具备**内嵌 ICU 方案**（见 D:\projects\icu），
  ICU 数据内嵌进二进制，不破坏「可嵌入、零外部运行依赖」卖点。ICU 作为可选增强，核心路径不依赖它。
  详见 [ADR-003](003-unicode.md)。

### 5. 嵌入 API

- 对外提供纯 C/C++ API（`neo/runtime.h` 之类），不暴露内部对象模型。
- 外部可注册自定义原生模块（native module registry）。

## 后果

- 优点：可控性强、无重依赖、字节码天然支持协程/生成器/挂起恢复、嵌入友好。
- 缺点：工作量大；标准覆盖需长期迭代；性能优化空间大（后期可做 JIT 等）。
