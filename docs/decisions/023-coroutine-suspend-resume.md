# ADR-023: 协程挂起/恢复 — yield/await 与参数桥接

- 状态: 已接受 (2026-11-02)
- 决策者: aserjoker（项目负责人） + CodeAgent
- 关联: ADR-004（执行模型）、ADR-017（Interrupt）、ADR-022（函数调用）

## 背景

确定协程（yield/await）的挂起与恢复机制。

## 决策

### 1. yield/await 是函数调用模型的自然延伸

基于已定的执行模型（每次调用一个 VM + Interrupt 挂起状态），
协程很好实现：**VM 不只是保存现场，还给了外部操作栈的机会**。

### 2. 挂起流程（yield / await）

```
b = yield;

执行到 yield：
  VM 挂起（保存现场：操作数栈/PC/作用域/栈帧）
  产生 Interrupt(yield) 返回给外部（ADR-017，携带挂起状态）
```

### 3. 恢复流程（next(param) / await 结果注入）

```
外部恢复（next(param)）：
  先把 param 压到 VM 栈上（外部操作栈的机会）
  再恢复 PC
  → 自然执行到 store "b"（消费栈顶 param）
  → 完成 VM 内和外部的参数桥接

await 同理：
  结果由外部压入 VM
  VM 恢复执行，下一行自然就是 store 或 pop（消费压入的结果）
```

### 4. 关键机制

- **VM 不只是保存现场，还给了外部操作栈的机会**：挂起后外部可以向 VM 栈压入值。
- **恢复时先压栈再恢复 PC**：被挂起的「取栈顶」指令（如 `store "b"`）自然消费压入的值。
- **yield/await 的传值语义天然成立**：
  - `yield` 恢复时 `next(param)` 的参数 = 压栈 → `b = yield` 的 b 收到它。
  - `await` 恢复时结果 = 压栈 → 后续 store/pop 消费。

### 5. 与既有模型的关系

- **VM 栈模式**（ADR-004）：操作数栈是统一的传值通道。
- **Interrupt 挂起状态**（ADR-017）：yield/await 携带 PC/栈/作用域，恢复时重建。
- **函数调用模型**（ADR-022）：invoke 统一入口，挂起恢复只是
  「中断 + 外部压栈 + 恢复 PC」。

## 推论

- 生成器/async 各自是独立 VM 实例，天然可挂起可恢复。
- 挂起点的传值不依赖额外机制，只是「外部压栈 + 恢复后自然消费」。

## 后果

- 优点：协程实现简单自然、传值语义天然正确、与既有模型无缝衔接。
- 缺点：挂起状态需完整保存（PC/栈/作用域），恢复需重建。
